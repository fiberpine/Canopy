## 0 结论

1. **零优化结果：上一轮登记的预测，除E-B的约束比例外全部通过。** P1、P1b、P2（12/12）、P4、锚点（4/4）都成立。
2. **E-B未过，是我把阈值定错了，不是隐藏的失败。**
   - 同一探索下，从未触到上限的G12-R200本身就是0.44/0.47。大缓冲后的G48/G72-R200为0.45–0.47，与它完全一样。
   - 快照代理（packets_out≥0.9·cwnd）在长RTT下受每步窗口抖动影响，稳定在0.45左右。
   - 判断窗口是否起作用，应看"无锚比例<0.1"，它通过了（0.001–0.002）。
   - 我补了一个对抖动稳健的RTT窗口代理，请GPT用现有日志零TCP复核（第4节）。
3. **更正：默认上限首先来自接收窗口。**
   - 只放大发送缓冲，在途量不变（3.19–3.23 MB）；只放大接收缓冲，升到3.7–3.8 MB（G48-q2先触到网络上限）；两侧都放大，才由网络限制并出现丢包。
   - 我上一轮说"数值上更接近发送缓冲"是错的。发送缓冲是第二道上限。
   - GPT的修正也接受：超过上限时增窗无效，减窗到上限以下仍然有效。
4. **大缓冲下101–253 ms的排队，是未训练策略的正常表现，不是环境问题。** 未训练策略约等于CUBIC加抖动和量化漂移，这与普通R200格一致（G12-R200 zero_sum为178/255 ms）。
5. **同意下一步做Orca单动作有限学习验证（L1）。但GPT列的三个失败模式，需要换一种判读方式：**
   - **强负动作本身不是病。** R20下cwnd<ssthresh时，内核每个RTT把窗口翻倍；要保持窗口，动作就得在−0.4~−0.5左右。归档的健康baseline就是−0.46~−0.55，利用率89–95%。所以要看利用率和饱和（|π|≥0.95），而不是动作的符号。
   - **历史上的早期塌缩出自control臂，不是moving臂。** 那次塌缩是π→−1、cwnd 6–9，在217k转移、2万次critic迭代内24/24个actor全部出现；control臂的actor损失用batch统计BN。moving臂从未饱和。L1用moving臂，所以"没有塌缩"只是弱检验。
   - **奖励虚高只在max_bw未锚定时出现。** 每个actor只有一条长连接时，max_bw在开头就被CUBIC式起步锚定，训练曲线里几乎看不到这个问题。它出现在每次评测的冷启动（A0）。所以必须靠评测中A0对A4g的差来测。E2已在历史moving终点上看到这一点：G48-R20的A0为36.4%，A4为94.8%。
6. **L1是一次单seed、约1小时的检查。**
   - 历史moving模板，加上零优化已验证的组件，再加有限预算。
   - 环境为64 MiB主机缓冲。
   - 评测共110次冻结运行。
   - 判定规则事先登记，由脚本自动套用（第3节）。

**约束代理为什么在0.45附近：**
- zero_sum每步改变一次cwnd。在途量只能在约一个RTT内跟上，所以cwnd/packets_out的中位数约1.05（R20）到1.2（R200），P95约1.4–1.66。
- 在途量追不上向上的跳变时，快照比较就会判为"不受约束"。因此这个比例随RTT下降：R20为0.61–0.66，R100为0.49–0.54，R200为0.34–0.47。
- 合成验证：cwnd按4^{o_t}抖动（σ_o=0.2/√2），在途量取过去10步中位数的0.87倍。复现出快照比例0.48、cwnd/packets_out中位1.12、P95 1.56，与实测几乎相同；同一数据的RTT窗口代理为1.00。
- 端主机上限的合成例中，两种代理都是0。

**附带观察：**
- seed 3小初始化的确定性项为每步−0.0047~−0.0064，seed 4为+0.0033~+0.0054。
- 加上取整项后，16次zero_sum的命令漂移都为负（−0.0003~−0.022/步），由内核增长补偿。
- 未训练策略的行为由CUBIC主导，排队接近CUBIC。

## 3 L1方案

**训练（与历史moving模板相比，只改下列键）：**
- `verified_ipc_v2=true`，server用`orca-server-verified-ipc`（正常CUBIC启动）。
- `scalar_window_initialization=small_uniform`。
- `exploration_process=zero_sum_offset`，ρ=0，σ=0.2。
- `sample_budget=1.2M`，`checkpoint_interval=100k`。
- 不变：奖励、网络、int(100·4^a)映射、moving-stat actor损失、24条件（2BDP）、24 actor、每actor一条连接、立即接管、UTD 0.1、warmup 12288、replay 300k、seed 3。
- 生成器断言探索、IPC、初始化和learner相关键与零优化验证任务一致。

**环境：**
- 所有actor主机的`tcp_rmem`/`tcp_wmem`最大值设为64 MiB，`rmem_max`/`wmem_max`同。
- 只有BDP+queue>约2070包的条件受影响（G42/G48/G72-R200-q2），其余条件从未触到旧上限。
- 前后记录回执。
- 建议此后所有训练和评测（含CUBIC/BBR/Orca/Canopy参照）统一用这一环境。

**监控（每30 s，`learning_monitor.py`）：**
- S1：|π|≥0.95占窗口一半以上的actor，3个告警，12个停止。
- S2：cwnd≤10占窗口一半以上的actor，3个告警，12个停止。
- S3：任一cwnd≥1e6，停止。
- 同时报告利用率（按goodput容量）、max_bw锚定比、自身与特权奖励、alias、排队、丢包，以及learner的Q、actor梯度和梯度消失。

**评测（冻结、确定性、同环境，每次60 s，共110次，约40分钟）：**
- 10个格：8个零优化格，加G48-R50（E2正常守门格）和G72-R100（E2弱格）。
- A0：checkpoint 0/200k/400k/800k/1.2M都跑，终点跑两次（A0锚定是双峰的）。
- A4g：只在400k和终点跑。下限取0.963×容量，即goodput；只作诊断，不是可部署结果。
- CUBIC参照：每格一次。
- 历史moving终点（step-3557457）的A0/A4g：只作对照，不进入判定。
- 每次记录binding_rtt、ss_mode、π与饱和、奖励与alias。

**预测（运行前登记）：**
- **P-L1：** 1.2M内没有STOP，|π|≥0.95低于每个actor窗口的10%，没有≥1e6。这是弱检验。
- **P-L2（描述）：** R20 actor在cwnd<ssthresh时学到负π，训练窗口利用率≥0.9。
- **P-L3：** 终点A4g−A0利用率≥0.15，至少出现在4个R20格中的2个，即复现E2。
- **P-L4：** 每个R200格|π(终点)−π(0)|≤0.05，A0排队变化在±25%以内。
- **P-L5（对照，不判定）：** 在G24-R100、G72-R100和3个R200格，终点A4g利用率≥0.90且排队不超过CUBIC。这些正是历史训练中爆窗的条件。

**判定（`adjudicate_learning.py`，按优先级；所有触发项都会列出）：**

| 判定 | 条件 | 下一步 |
|---|---|---|
| COLLAPSE_REPRODUCED | 监控出现STOP | 审计第一个饱和actor的critic方向与数据支持，再定变量 |
| POLICY_LIMITED | A4g利用率<0.80的R20格≥2 | 离线审计R20状态的critic方向；再选一个变量（actor饱和保护或延迟项） |
| ANCHORING_LIMITED | A4g−A0≥0.15且A4g≥0.90的R20格≥2 | 在L1终点上做冻结E2b（A0 / 观测结束的锚定接管 / A4g）；再做一个带连接重置和该接管协议的训练臂 |
| LONG_RTT_STATIC | P-L4成立 | 先做ρ>0（匹配稳态偏离）的零优化检查 |
| GO_LONG_TRAINING | A0达标（利用率≥0.9、排队与丢包不差于CUBIC）≥8/10，A4g−A0≤0.10≥8/10，最后三分之一无告警 | 3 seed×2.4M长训，同一监控与评测 |
| PARTIAL | 其余 | 按趋势；A0排队/CUBIC随checkpoint单调下降且利用率稳定时，才延长到2.4M |

我的预期：L1多半判为ANCHORING_LIMITED，并可能同时触发LONG_RTT_STATIC。即便如此，它也回答了两件事：修复后的流水线有没有引入新失败；A4g的上限质量比历史好多少。

## 5 L1不做的事

- 连接重置；
- 训练中的锚定接管；
- 奖励或归一化改动；
- ρ>0；
- 网络或窗口映射改动；
- MTP或双动作。

每一项都等L1判定后，单独作为变量处理。
