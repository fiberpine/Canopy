# 五机利用率低，是否应该增加actor

2026-11-12。**现有五台可以尝试增加并发actor，但不能按整机空闲CPU线性扩到48/256，也暂不建议再租actor服务器。优先检验现有五机的32actor资源准入，再有条件试48；是否支持当前U=.1，需要当前执行链实测。** 本轮分析0实验服务器连接、0新TCP或TF优化，当前不用保持服务器开启。

## 为什么CPU只有30%—50%，learner仍可能跟不上

机器是8个逻辑CPU。整机47%表示约3.8个逻辑CPU的平均忙碌量，不代表每条串行路径都还有53%吞吐空间，且逻辑线程并不等于独立物理核心容量。

当前代码明确将**策略前向、两个critic、actor、target和共享FIFO放在learner CPU**。actor服务器负责TCP/Mahimahi和Python控制，再远程调用learner推理/入库。因此四台actor机闲，不能自动拿来分担learner的优化。TF线程数固定为4，优化循环按critic→actor/BN→target顺序发起；TensorFlow内核有并行，整个更新链却不是任意并行的五台计算池。

还可能受Python采样/入库调度、频繁小RPC、线程池同步或内存访问约束；这些是待剖析候选，不是已经确定的GIL/带宽唯一瓶颈。旧H0记录critic约2.52ms、actor/BN约2.47ms、target约0.60ms，仅这三段顺序工作约5.58ms；其倒数约179次/s仍未计采样、调度等。不能根据整机CPU外推到每秒上千次更新。

另一个反向因果：坏策略缩到低窗口后，ACK/有效反馈减少，入库和优化需求也下降，CPU自然降低。不能用坏策略低负载状态来估计健康高吞吐状态的扩容空间。容量准入采用中性执行、仍保留实际推理/优化，正是为了避免这个误判。

增加物理actor服务器以前，应先查learner：逐核CPU、user/system/softirq/steal/iowait、进程及线程忙碌、采样/入库耗时、各更新阶段、推理/入库RPC、实际控制周期、磁盘吞吐和FIFO/更新信用。简单调大TF线程数也未证明有效，会与并发推理争资源；先做同负载短测。当前计算显式放CPU，租GPU不会自动让这条路径用上GPU。

## 不能直接改一个--actors就把结果解释为集群收益

当前入口循环复制24条件，replay按actor均衡。直接改32时，只有前8条件被复制两次，其余16条件一次，学习权重随之变化；它可以是**资源压力探针**，不能当只改并发度的算法对照。48恰好把完整24网格复制两遍，条件权重才基本保持一致，但覆盖仍只有24，并没有变成48个不同条件。若要更多不同条件，须另登记覆盖及连接/history/max_bw语义。

增加actor还会改变热身：每actor至少512条的覆盖门，48个最低就需24576条。保留12288名义warmup会积累更大的开闸信用，启动阶段债务不能和稳态不足混算。batch512下每actor配额也从约21行降为约10行。若将来只增加并发以提速，必须固定条件权重、总真实样本、完整更新额度和评测口径，不能悄悄降低U让欠额消失。

大FIFO、延长等待或减少更新次数可以掩盖压力，不能证明原学习配方扩容通过。本轮没有改它们，也没有新的性能收益结论。

## 当前建议和一轮可执行短测

**先用现有五台，不购买新机器。** 要确认当前执行链是否能支持32/48，需要开机做一次有界容量测试；仅本机资料无法给出可信最大值。先离线准备配置/计数和资源采样，开机后统一当前图配置与同一个已校验native文件，每组全新随机模型/replay，固定中性执行但保留真实远程推理和完整优化，不作为算法训练结果。

建议新窗口**最多30分钟，五台保守2.5机时，最后5分钟收尾**：

1. 前置：核对五机身份/内核/源码/二进制/端口及历史保护文件；最多约90秒learner-only真实批内存更新微测，只估无actor干扰的上界，不保存可用模型或写旧checkpoint。
2. 24actor参照，最多240000条真实经验；当前U=.1、150k回放、真实满回放及停止前live保存、来源/映射/最终信用排空一起检查。
3. 24通过后32actor资源探针，同样最多240000条；明确其条件复制权重不同，绝不报告学习质量。若服务不足、RPC/控制周期明显恶化或清理失败，停止扩容。
4. 32通过且剩余时间足够，才48actor同完整24网格双副本压力准入，最多240000条；否则记NOT_RUN。三个上限都能整除actor数，不重复上一轮准入配额错误。窗口内意外执行失败可修正重测，但总时长和最多三组网络任务（含重测）不增加。

验收同时看已生成/入队/入库一致，完整更新等于floor((N−warmup)×.1)、critic操作为两倍、最终欠额0；稳态至少60秒、欠额斜率不持续为正，记录启动信用和消化过程。建议工程门：各actor推理RPC P95≤2ms、固定中性负载控制P95≤30ms、无协议/数值/入库故障；这些是待执行容量门，不是论文标准或健康策略门。FIFO持续增长或稳态欠额持续上升即提前停，不能拖到总预算耗尽才发现。

每两秒记录逐核和主进程资源；原始逐包和大checkpoint/replay留云端，仅回传小指标/源哈希。最后核对本轮进程、IPC、监听端口和保护文件。**本方案尚未执行，也未获新费用授权；当前不用开机，批准该窗口后再开机通知。**

如果32/48在U=.1下通过，才得到更高并发的工程准入，之后仍需单独登记正式训练与健康验收；若失败，先优化/配置learner或调整计算布局，再考虑加硬件，而非盲加actor服务器。
